一个围绕减重/体重管理的个人健康追踪小工具: 在「记录每日体重并自动计算移动平均(默认 **3 日 / 7 日**)」的基础上, 进一步提供 **BMI 健康分界导航**、**目标体重与减重进度(减重期/维持期自适应)** 与 **放纵记录及坚持天数激励**, 把数据转化为"下一步该怎么做"的反馈。后端基于 FastAPI + SQLite, 前端为原生 HTML/CSS/JS, 包含录入表单、统计卡片、趋势图与历史记录表。

## 功能特性

- 录入每日体重(必填, 单位 kg)与备注(可选)。
- 日期在页面打开时自动取本地当天日期(`yyyy-mm-dd`), 也可手动修改。
- 同一天重复提交会覆盖更新(一天一条)。
- 自动计算移动平均: 默认 3 日与 7 日, 可在 `.env` 中通过 `MA_WINDOWS` 调整。前端会按接口返回的窗口**动态渲染**统计卡片、表格列与趋势曲线, 修改 `MA_WINDOWS` 无需改前端代码。
- 趋势图同时展示体重曲线与各窗口的移动平均曲线。
- 支持删除任意一天的记录。
- 个人档案(身高): 身高作为不随日期变化的全局信息单独存储, 页面顶部默认**只读展示**, 点"编辑"才可修改, 不会被每日录入误改。设置身高后, 统计卡片会自动以**最大窗口均值**(默认 7 日均值)计算并展示 **BMI**, 避免单日称重噪声影响数值; 记录不足时回退为最新体重。BMI 数值下方还会给出一行**单边界导航**副信息: 按当前所处区间与减重方向, **只指向下一个最近的健康分界**并以 kg 为主、BMI 为辅给出可执行差距(肥胖→「还需减 X kg 进入超重(BMI 28.0)」, 超重→「进入正常(BMI 24.0)」, 偏瘦→「还需增 X kg 进入正常(BMI 18.5)」, 正常区则提示「已在健康区间」并附距超重的缓冲)。换算口径为 Δ体重 = ΔBMI × 身高(m)², 把"健康标签"转化为"下一步还差多少", 与下方按个人目标体重计算的「目标进度」格互补(一为客观健康里程碑, 一为个人目标)。
- 目标体重与减重进度(**阶段自适应**): 在页面顶部设置**目标体重**与**起点日期**(默认设定当天, 可改为其他日期, 用于定位"起点的 7 日均值")后, 统计卡首格变为「目标进度」并随阶段自动切换语义——**减重期**展示「已减 X kg」与「进度 X%」; 当 7 日均值进入 **目标 ±band** 区间(半宽 band 由 `.env` 的 `TARGET_BAND` 配置, 默认 1.0 kg, 视为达标)后自动切换为**维持期**, 展示「偏离 ±X kg」与「已维持 N 天」, 使减到目标后该卡片依旧有效。所有判定与计算均基于**最大窗口均值**(默认 7 日均值)而非单日体重, 避免单日称重噪声误判。考虑到最新体重噪声大、用户更关注均值变化, 统计卡不再单独展示"最新体重"。统计卡末格展示 **「较上周 7 日均值」(周环比, 默认窗口 7 时的表述; 自定义窗口时为「较上一 N 日均值」)**: 以**当前最大窗口均值**减去 **N 天前的同窗口均值**(默认即"本周 7 日均值 vs 上周 7 日均值"), 两边均为均值而非单日体重, 按日历日定位上期(缺记时取该日前最近一条记录的均值), 数值落在健康减重速率尺度且不受单日称重噪声影响。记录不足约两周时, 上期均值按当时已有记录回退计算(窗口可能不满, 早期偏噪声); 完全缺少早于上期日期的记录(约不足一周)时显示 `--`。
- 放纵记录: 单独记录"喝酒/吃好吃的"这类放纵行为(**类型可多选**, 一次同时喝酒又吃也能记一条), 并标注**触发原因**(压力大 / 奖励自己)。约定**一天一条**(同日重复提交按日期覆盖, 选到已有记录的日期时按钮变"更新记录"并提示将覆盖), 与每日体重解耦; 列表支持**内联编辑**(修改类型 / 触发原因 / 备注)与删除, 备注过长时**悬浮显示完整内容**。页面突出展示 **「已坚持 N 天没放纵」** 横幅, 并在其下同时给出 **历史最佳** 与 **上一段坚持天数**: 既靠"不要断签"约束自己, 又用"刷新个人纪录"提供正向目标——即便今天破功归零, 也能看到过往成绩与可超越的目标(当前坚持超过此前所有已结束坚持段时会高亮提示"正在刷新纪录")。同时在趋势图上以**竖虚线 + 🍺/🍰 标记**标出放纵日, 直观对比"放纵之后体重曲线是否抬头"; 放纵当天若没称体重(如放纵次日不敢称), 标记会**就近吸附到其后第一个称重日**(该点正是"放纵后第一次称重"), 悬浮提示中会标注实际放纵日期, 其后尚无称重记录的放纵待下次称重后自动显示。

> **坚持天数口径**: N 取"**完整度过的干净自然日**"数量, 即今天与最近一次放纵日的自然日差再减 1。放纵当天与次日均记为第 0 天, 之后每多过一整天 +1(例: 06-17 放纵, 06-18 显示 0 天, 06-19 显示 1 天)。是否"**今天破功**"单独按"最近一次放纵日 === 今天"判断, 与显示天数解耦——破功当天横幅会**变红、天数归零并提示"明天重新开始"**, 而次日(天数同为 0)不会再标红, 避免误判。**历史最佳 / 上一段** 沿用同一口径: 把相邻两次放纵之间视为一段"已结束坚持段"(同样按自然日差减 1), **历史最佳** = 各已结束段与当前进行中段一并取最大, **上一段** = 最近一次已结束段(即最后两次放纵之间, 仅一条记录时显示 `--`)。第一次放纵之前没有可锚定的起点, 故不纳入统计, 避免虚高。

> 移动平均口径: 采用"最近 N 条记录"(即 N 个数据点)的均值。对每条记录取其自身及之前共 N 条记录求平均; 不足 N 条时用已有记录求平均。该口径对存在缺录的日期更稳健。

## 前端静态资源版本号(缓存失效)

前端为原生静态文件, 浏览器会缓存 `style.css` / `app.js`。`index.html` 通过查询参数做**手动缓存失效**:

```html
<link rel="stylesheet" href="/static/style.css?v=9" />
<script src="/static/app.js?v=7"></script>
```

**约定: 每次修改 `static/style.css` 或 `static/app.js` 后, 必须把对应的 `?v=N` 版本号 +1**(两文件各自独立计数)。否则浏览器可能继续使用旧缓存, 导致改动"看起来没生效"——常见表现是样式错乱(如新加的 CSS 类未生效)或 JS 行为还是旧的。

> 排查技巧: 若怀疑是缓存问题, 可临时在地址后加随机参数强制拉取最新 HTML(如 `http://127.0.0.1:8421/?nocache=1`), 或在浏览器开发者工具的 Network 面板勾选「Disable cache」后硬刷新。确认无误后仍应回到"升版本号"这一正规做法。

## 依赖说明

项目把依赖拆成两个文件, 二者是**互补关系**(而非重复), 用于区分"生产运行需要的"和"只有开发/测试才需要的":

| 文件                   | 用途       | 内容                                              | 安装场景         |
| ---------------------- | ---------- | ------------------------------------------------- | ---------------- |
| `requirements.txt`     | 运行依赖   | FastAPI、uvicorn、aiosqlite、loguru、python-dotenv | 生产、开发都需要 |
| `requirements-dev.txt` | 测试依赖   | pytest、httpx                                      | 仅开发/测试需要  |

这样拆分的好处:

- **生产部署更精简**: 线上只装 `requirements.txt`, 不会把 `pytest` 等测试工具带到生产环境, 减小体积与攻击面。
- **职责清晰**: 一眼区分核心运行依赖与辅助开发工具。

安装方式:

```bash
# 生产环境: 只装运行依赖
pip install -r requirements.txt

# 开发环境: 运行依赖 + 测试依赖都要装
pip install -r requirements.txt
pip install -r requirements-dev.txt
```

> `requirements-dev.txt` 未通过 `-r requirements.txt` 引入运行依赖, 因此开发环境需分别安装两个文件。

# 1. 创建并激活 conda 环境

## 后台运行

后台模式默认关闭热重载(`.env` 中 `RELOAD=false`), 保证单进程, 停止时不会残留孤儿进程。

```bash
# 启动: 输出重定向到日志文件
conda activate weights
nohup python -m app.main > logs/server.log 2>&1 &

# 查看实时日志
tail -f logs/server.log
```

查看服务是否在运行(端口取自 `.env` 的 `PORT`, 默认 8421):

```bash
lsof -i:8421          # 查看占用 8421 端口的进程
```

停止服务(按端口号, 精确结束监听该端口的进程):

```bash
lsof -ti:8421 | xargs kill
```

### 如何判断服务是否真正在运行(LISTEN vs CLOSED)

`lsof -i:<端口>` 的输出未必代表服务已启动, 需要看 `NAME` 列末尾的连接状态:

- **`(LISTEN)`**: 有进程正在**监听**该端口, 说明服务已启动。例如:

```
COMMAND   PID  ...  TYPE  ...  NODE NAME
python    xxx  ...  IPv4  ...  TCP 127.0.0.1:8421 (LISTEN)
```

- **`(CLOSED)`**: 只是**已关闭的客户端连接**残留(常见于浏览器之前访问过该端口), 并非服务在监听。例如:

```
COMMAND   PID            USER  ...  TYPE  ...  NODE NAME
Google  91875   peilongchencc  ...  IPv4  ...  TCP localhost:59682->localhost:8421 (CLOSED)
```

> 说明: 部分系统会把端口号显示为服务别名(如 8000 显示为 `irdmi`)。`->` 箭头表示该进程是作为**客户端**主动连出, 而非监听端口。这类 `CLOSED` 连接会被系统自动回收, 无需处理。

加 `-nP` 可禁用端口别名与主机名解析, 输出更直观; 也可只筛选监听状态来明确判断服务是否启动:

```bash
lsof -nP -i:8421                         # 不解析别名/主机名, 输出更清晰
lsof -nP -iTCP:8421 -sTCP:LISTEN         # 仅看监听状态, 无输出即服务未启动
```

## 接口说明

所有响应均为统一结构, 并包含用于日志追踪的 `request_id`。`request_id` 由中间件统一生成, 同时回填到响应头 `X-Request-ID`, 便于客户端与服务端日志对齐。即使发生未捕获异常, 也会返回统一结构(`code=500`)并携带同一 `request_id`。

| 方法   | 路径                  | 说明                       |
| ------ | --------------------- | -------------------------- |
| POST   | `/api/records`        | 新增/更新一天的体重记录    |
| GET    | `/api/records`        | 查询全部记录(含移动平均)   |
| DELETE | `/api/records/{date}` | 删除指定日期的记录         |
| GET    | `/api/profile`        | 查询个人档案(身高 + 目标体重) |
| PUT    | `/api/profile`        | 设置/更新身高(单位 cm)     |
| PUT    | `/api/profile/target` | 设置/更新目标体重与起点日期 |
| POST   | `/api/indulgences`    | 新增/更新一天的放纵记录(同日覆盖) |
| GET    | `/api/indulgences`    | 查询全部放纵记录(最新在前) |
| PUT    | `/api/indulgences/{id}` | 编辑放纵记录(类型/触发/备注) |
| DELETE | `/api/indulgences/{id}` | 删除指定 id 的放纵记录   |

> 身高与目标体重同存于单行 `profile` 表: `height_cm`(取值范围 50-300 cm)、`target_weight`(目标体重 kg)、`target_start_date`(起点日期 yyyy-mm-dd)。三者与每日体重记录解耦, 且**各字段独立写入**(`PUT /api/profile` 仅改身高, `PUT /api/profile/target` 仅改目标, 互不覆盖)。其中 `target_weight` 须 > 0, `target_start_date` 须为合法 yyyy-mm-dd 且**不晚于今天**(后端校验, 与前端日历"禁止选未来日期"一致)。前端据身高与最大窗口均值(默认 7 日均值)计算 BMI, 据目标与起点日期的均值计算减重进度/维持情况; **维持期的「已维持 N 天」按自然日(日历天)计算, 而非记录条数**, 中间有缺记的日期也能反映真实天数跨度。历史库缺少目标相关列时, 服务启动会自动补列(幂等迁移)。

> 放纵记录存于 `indulgences` 表, 每条含 `date` / `kind` / `trigger`(`stress` 压力 / `reward` 奖励) / `note`。其中 `kind` 支持**多选**, 取值为 `alcohol`(喝酒) / `food`(吃好吃的), 请求体用数组字段 `kinds`(如 `["alcohol","food"]`, 至少一项), 库内以逗号拼接存于 `kind` 列、读取时拆回数组。约定**一天一条**: `date` 列建唯一索引, 同日 `POST` 按日期 upsert 覆盖并复用原 `id`; `PUT /api/indulgences/{id}` 可编辑类型/触发/备注(日期不变)。「已坚持 N 天」及衍生的**历史最佳 / 上一段坚持天数**均由前端基于全部放纵记录计算(口径为"完整度过的干净自然日"数, 即自然日差减 1; 放纵当天与次日均为第 0 天), 后端只负责存取。

请求示例(POST `/api/indulgences`):

```json
{ "date": "2026-06-18", "kinds": ["alcohol", "food"], "trigger": "stress", "note": "项目延期，喝酒又点了外卖" }
```

请求示例(POST `/api/records`):

```json
{ "date": "2026-06-16", "weight": 91.1, "note": "晨起空腹" }
```

响应示例:

```json
{
  "code": 200,
  "message": "记录保存成功",
  "request_id": "b1e7...",
  "data": { "date": "2026-06-16", "weight": 91.1, "note": "晨起空腹" }
}
```

## 配置项 (.env)

| 变量         | 说明                         | 默认值          |
| ------------ | ---------------------------- | --------------- |
| `HOST`       | 监听地址                     | `127.0.0.1`     |
| `PORT`       | 监听端口                     | `8421`          |
| `DB_PATH`    | SQLite 文件路径              | `weights.db`    |
| `LOG_PATH`   | 日志文件路径                 | `logs/app.log`  |
| `MA_WINDOWS` | 移动平均窗口(逗号分隔, 天)   | `3,7`           |
| `TARGET_BAND` | 达标/维持判定的区间半宽(kg) | `1.0`          |
| `RELOAD`     | 是否开启热重载(后台运行建议 `false`) | `false`   |
